## 0. 先修正五条事实（读完代码和 a.html 之后）

| # | 说法 | 实际 | 依据 |
|---|---|---|---|
| 1 | 现在一行 44px 只是"行高" | 44 = 7 内距 + 16（名字 12/600）+ 14（次行 11）+ 7。**没有一寸是装饰**，所以"加场景"只能换结构，不能在 44 里塞 | `client.js:372`、`387-388` |
| 2 | 7 个状态 | 确认 7 个：`failed / provisioning / working / waiting / done / error / idle`。`provisioning` 的文案是**「入职中」**，不是"组建中" | `client.js:628-635`、`98-104` |
| 3 | 侧边栏变窄时媒体查询能兜住 | 不能。栏宽变化窗口不变，`@media` 不触发。现有代码已经用 `@container` 兜（340 / 560），新布局必须沿用 | `client.js:488-491` |
| 4 | `bg-layer-1/2/3` 是三档层次 | **亮色下三档全是 `#fff`**。实测 `@deepseek-ai/dsh-client-ui-theme/lib/client.js`：`body` 块里三个 alias 都指向 `--dsw-static-neutral-bluish-00`。暗色才有 `#232324 / #2c2c2e / #353638` | 主题包实测；a.html 独立得出同一结论（`a.html` 注释：「浅色主题里 bg-layer-1/2/3 全是纯白」） |
| 5 | 交接信号能直接驱动"走过去" | **不能**。`out` 存活 1600ms，`in` 只活 **480ms**；而走路要 900ms 才到对方工位。目标行的标记会在信使到达前 1120ms 消失 | `client.js:524-526`、`541-554`、`384` |

第 4 条是本轮最重要的一条：**亮色主题下场景的层次不能靠底色**，只能靠「深色实物 + 描边 + 状态色的一束光」。这决定了下面所有 cell 的画法（`desk.svg` 里家具一律中性描边，显示器是墨色实物）。

第 5 条是一处必须改的代码（不是设计意见）：`handoffDuration('in')` 要从 480 提到 1600，目标行的闪底改用 `animation-delay: 1100ms` 触发。见 §4。

## 1. 预算：280px 里能放什么

| 栏宽 | 内容宽（减 20 内距） | 场景 |
|---|---|---|
| 380 | 360 | 常见 |
| 320 | 300 | 用户拉窄 |
| **300** | **280** | **框架下限，所有 cell 按这个画** |

三个方向都按 **280** 出图，所以"300px 下怎么退化"这个问题，对 B 来说答案是**零退化**（它本来就是最窄形态），对 A 是"每格 127"，对 C 是"永远滚动"。

一个额外的硬约束：`MAX_TEAM_SIZE = 8`（`lib/roles.js:9`）。所以"8 人"不是上限情况，是唯一情况。这直接决定了 A 的网格恰好是 4×2，不用考虑第 9 个人怎么办。

## 2. 三个方向

三个方向不是同一套换色，是**三种空间隐喻**：A 是**平面图**（从上方看一个房间），B 是**走廊**（站在走廊里看两侧），C 是**斜视房间**（从角落看进去）。

### 方向 A · 俯视网格

**一句话：值班表长出了一张脸 —— 先看到「两列整齐的后脑勺 + 一片显示器光」，再看每格下面的名字。**

```
内容 280 = 127 + 26 过道 + 127
┌─────────── 127 ───────────┐        ┌─────────── 127 ───────────┐
│      ▛▀▀▀▀▀▀▀▀▀▜          │        │      ▛▀▀▀▀▀▀▀▀▀▜          │
│      ▙▄▄▄▄▄▄▄▄▄▟  ← 显示器 │        │      ▙▄▄▄▄▄▄▄▄▄▟          │
│          ( ◕ )    ← 后脑勺 │  26    │          ( ◕ )            │
│      ▁▁▁▁▁▁▁▁▁▁▁  ← 桌沿   │ 过道   │      ▁▁▁▁▁▁▁▁▁▁▁          │
│        小前 · 干活中        │   ‖    │        小审 · 等你回复     │
└────────────────────────────┘        └───────────────────────────┘
每格 86 高（美术 54 + 铭牌 24 + 8）；8 人 = 4 行 = 344 + 组头 28
```

| 项 | 值 |
|---|---|
| 扫视顺序 | 先看「两列光斑的疏密」判断忙闲，再看格下的名字定位到人 |
| 每格内容 | 显示器（78×32，含屏幕字形）+ 后脑勺 30 + 桌沿 2px + 椅背 + 名字/状态两行 |
| 8 人总高 | 344 + 28 = **372**（栏高 600 里不滚动） |
| 主信号 | 屏幕字形 + 光晕（状态）／格下铭牌（身份） |
| 300px 退化 | 零结构变化。格宽固定 127，名字 4 字顶满，状态文案 4 字仍在 |
| 走动 | 竖向过道 26px，横一步 + 纵 N 步；**26px 比 32px 的吉祥物窄**，走过去会压两边桌沿 |
| 实现代价 | 中。一个 grid，格 = 现有 `.wt-row` 的同构替代（一个成员一个 button） |
| 主动放弃 | 放弃「名字成一列」。名字在格下居中，扫视变 Z 字，这是 A 与 B 最本质的差别，不是密度 |

A 现在**已经实现**（`a.html`），而且实现得比我原提案好一处：它把过道做成了**竖向 26px 带 + 中间虚线**（`.floor::before/.after`），而不是我原来写的"行间横向缝隙"。这是对的，因为走动在竖向上更顺。本 spec 采纳它的做法。

### 方向 B · 单列走廊

**一句话：一条走廊 —— 先看到「走廊上有没有人在走」，再看两侧工位的显示器光和名字。**

```
内容 280 = 桌 116 + 走廊 40 + 文字 124
┌──────────────────────────── 280 ────────────────────────────┐
│ ▛▀▀▀▀▀▀▀▜                                                   │
│ ▙▄▄▄▄▄▄▄▟        ┊                                           │
│   ( ◕ )          ┊        小前                              │
│ ▁▁▁▁▁▁▁▁▁        ┊        前端 · 改登录页的错误提示…        │
│                  ┊  走廊    ▁ 干活中                        │
├──────────────────┊──────────────────────────────────────────┤
│                  ┊        ┌────────────┐                    │
│        ┊         ┊        │ ▛▀▀▀▀▀▀▀▜  │  ← 右桌变体        │
│        ┊         ┊        │   ( ◕ )    │                    │
│        ┊         ┊        │ ▁▁▁▁▁▁▁▁▁  │                    │
└──────────────────┴────────┴────────────┴────────────────────┘
每行 64（美术 56 + 铭牌并入文字列）；8 人 = 512 + 组头 28 = 540
```

| 项 | 值 |
|---|---|
| 扫视顺序 | 先看走廊（有没有人在走 = 有没有交接正在发生），再看右列的名字与状态 |
| 每行内容 | 场景 116（显示器 + 后脑勺 32 + 桌沿 + 椅背）／走廊 40／文字 124（名字 12/600 + 角色·任务 11 + 状态） |
| 8 人总高 | **540**（600 的栏里刚好不滚动；480 的栏里要滚 60） |
| 主信号 | 状态：走廊上的走动 + 屏幕字形；身份：项圈 + 文字列 |
| 300px 退化 | **零**。cell 就是按 280 画的。栏变宽只加给文字列（144 → 224） |
| 走动 | 走廊 40 = 32px 吉祥物 + 4px 余量。每格自带出口，任何两人之间的路径都不穿过第三个人的工位 |
| 实现代价 | 中。一行 = 一个成员，和现在 `.wt-row` 同构，不需要虚拟化、不需要测量 |
| 主动放弃 | 放弃 2 列。8 人必须 8 行，比 A 高 168px。这是 B 唯一的代价 |

### 方向 C · 等距斜视小房间

**一句话：从角落看进去的一间间小屋 —— 先看到「一间间亮着的小房间」，再看房间里是谁。**

```
内容 280，一间 108 高（地面菱形半宽 80 / 半高 46 = 29.9°）
┌────────────────── 280 ──────────────────┐
│              ╱▔▔▔▔▔▔╲                    │  ← 显示器（侧对镜头）
│            ╱  ( ◕ )   ╲                  │
│          ╱ ▁▁▁▁▁▁▁▁▁▁▁  ╲                │  ← 桌面菱形
│          ╲              ╱                │
│            ╲__________╱                  │
└─────────────────────────────────────────┘
8 人 = 864 + 组头 28 = 892 → 1.5 屏
```

| 项 | 值 |
|---|---|
| 扫视顺序 | 先看房间（谁那儿亮着），再看房间里的人 |
| 8 人总高 | **892**（必须滚动，A 的 2.4 倍） |
| 主信号 | 光晕（唯一还能读的状态通道） |
| 300px 退化 | **退化不了**。见下 |
| 走动 | 斜向路径 = 两轴同时插值，纯 CSS keyframes 要做 4 段；而且走动时会被前排房间的桌沿挡住 |
| 实现代价 | 最高。三套 cell 里唯一需要自己算投影的 |

C 的真实代价不是"高"，是**它在这个宽度里放不下自己**：

1. **放得下地面，放不下墙。** 30° 菱形 160 宽就要 92 高；一面 34 高的墙要再吃掉 34。一间带墙 = 150 高，8 人 = 1200px。
2. **放得下桌子，放不下屏幕。** 显示器在这个角度近乎侧对镜头（`desk.svg` 的 C 格），屏幕放不下任何字形 —— 于是 C 只剩光晕一个状态通道，而 A/B 有「光晕 + 字形」两个。
3. 把 30° 压成 3:1 能塞进 64 高，但那时它不是"房间"，是"一张带斜地板的卡片"，也就是 B 换了张贴图 —— 用 C 的名字卖 B 的货。

**结论：C 不建议。** 除非办公室被当作品牌画面（比如产品介绍页截图），那时它不是侧边栏组件，是插画。

## 3. 三方向对照与推荐

| 维度 | A 俯视网格 | B 单列走廊 | C 等距房间 |
|---|---|---|---|
| 8 人总高（栏 380） | 372 | 540 | 892 |
| 不滚动？（栏高 600） | 是 | 是（余 32） | 否（1.5 屏） |
| 300px 退化 | 零结构变化 | **零** | 退化不了 |
| 名字排布 | 格下居中，Z 字扫视 | **一列对齐，竖轴扫视** | 斜格内，最难扫 |
| 状态通道数 | 光晕 + 屏幕字形 + 铭牌点 | 同 A（+ 走廊走动） | 只有光晕 |
| 走动空间 | 26px（窄于角色） | **40px（角色 + 4 余量）** | 斜向且被前景遮挡 |
| 是否穿过别人工位 | 横跨时压两边桌沿 | **否** | 否 |
| 实现代价 | 中（已实现） | 中 | 高 |
| 已实现 | ✅ `a.html` | — | — |

### 推荐：B

三条理由，按重要性：

1. **只有 B 让「走动」成为空间本身，而不是贴上去的动画。** 老板的原话是"员工在办公室里走动、交接任务时递东西"。A 的过道 26px，比 32px 的吉祥物还窄 —— 走过去必然压两边桌沿，视觉上是"挤过去"；而且 A 的两列意味着任何跨列的交接都要横穿一次别人的格子。B 的每格自带一个 40px 出口通向同一条走廊，任意两人之间的路径长度只和行距有关。
2. **B 保住了现在列表唯一的优点：一列对齐。** 现有 44px 行把状态右对齐成一条竖线（`client.js:389`），这是"扫一眼知道谁在等我"的全部机制。B 的文字列 124px 让名字和状态继续成列；A 把它们挪到格下居中，扫视变成 Z 字。**这不是审美差异，是"找一个特定的人"和"扫一遍谁在忙"哪个更快的问题。**
3. **B 的下限最好。** cell 按 280 画，300px 栏就是它的常态，栏变宽只加给文字列。A 在 300px 下每格 127px，名字 4 字顶满，状态文案一旦换成"等你回复"就只剩省略号。

### 动效词汇：三个方向各用什么，不用什么

时长与曲线全部取自既有网格（`TOKENS.md` §5），三个方向共享同一套词汇，只是**用量的差别**。

| 方向 | 主要动效（每态进入时播一次） | 交接 | 明确不用 |
|---|---|---|---|
| A 俯视网格 | 屏幕字形淡入 120ms；环切色 160ms；`wt-bob 1.15s` ×3（不无限循环） | 沿竖向过道走；横向 1 格位移 78px | 不用逐卡 stagger（8 张卡依次亮会像加载）；不用卡片 `translateY(-1px)` 悬浮（网格里悬浮会破坏对齐） |
| B 单列走廊 | 同上 + 走廊上的信使是唯一持续位移的东西 | 走廊纵向走 + 两段 160ms 进出格 | 不用无限循环的呼吸（8 行同时在呼吸 = 一片噪声，只在进入状态时播 3 次） |
| C 等距房间 | 只有光晕呼吸（屏幕放不下字形） | 斜向双轴插值，需要 4 段 keyframe | 不用投影位移（房间会互相遮挡）；不用房间入场（8 间依次出现要 2s） |

一条通用规则：**静止时不播循环动画。** `client.js:282-285` 现在是 `infinite`（idle 呼吸 / working bob / waiting 摆），8 人同屏 = 8 个不同相位的循环 —— 在 44px 列表里还能忍，在场景里会变成一片抖动。改成「进入状态时播 3 次然后停」，状态由姿态 + 屏幕字形静态承载。

**a.html 已经把这条做对了**（`animation:wt-bob 1.15s ease-in-out 3`），所以这条不是要它改，是提醒后面移植时别退回 `infinite`。

### 什么时候该选 A

如果老板的真实诉求是**"列表太长/太挤"**而不是"不像办公室"，选 A：372 vs 540，A 省 168px，而且**已经跑起来了**。

A 已经实现，所以我不建议推倒。如果决定留在 A，最小改动是三条（都是加法，不重排 DOM）：

1. **给后脑勺加项圈。** `a.html` 现在的人是一个纯色圆 + 肩（无耳、无项圈、无尾），八个工位只能靠铭牌区分。换成 `mascot.svg` 的 `#state-*`（28–32px 下耳朵类别 + 项圈色 + 尾巴重量三通道）。
2. **过道从 26 加到 34。** 现在 26px 装不下 32px 的走动角色。加 8px 从两格各借 4px（127 → 123），名字仍放得下 4 字。
3. **屏幕补内容。** `a.html` 的屏幕现在是空面板 + 一条漏光线；`desk.svg` 的 7 个 `#scr-*` 可以直接替换进去（同一 78×32 盒子，一行 `<use>` 的事）。

## 4. 交接：1600ms 怎么切成四段

### 4.1 现有信号（不能改协议，只能改时长）

`flashHandoff(from, to, fromLabel, toLabel)` 在两端各留一个标记，keyed by **member name**：

| 端 | 标记 | 存活 | 现在的视觉 | 依据 |
|---|---|---|---|---|
| 源 | `{kind:'out', from:<对方label>}` | 1600ms | 行尾 `→ 小前` + 行底闪一次 | `client.js:541`、`1202-1204`、`384` |
| 目标 | `{kind:'in', from:<源label>}` | **480ms** | 行底闪一次 | `client.js:542`、`384` |

**必改一处**：`handoffDuration('in')` 480 → 1600（`client.js:524-526`），并把 `wt-flash` 拆成两个延迟：源行 `0ms`，目标行 `1100ms`。理由：信使 900ms 才到，480ms 的标记在到达前就消失了；而 `in` 的语义就是"东西到了"，它应该发生在到达的那一刻。

### 4.2 四段（总 1600ms，与 `out` 的生命周期严格同长）

| 段 | 时间 | 画面 | 通道 | 实现 |
|---|---|---|---|---|
| ① 起身 | 0–200 | 源格吉祥物切 `#state-handoff`（上身 −6°、尾上扬、抬手）；走廊里出现信使（`opacity 0→1`，80ms 内完成，位置=源格出口） | 姿态 + 出现 | 行加 `data-wt-handoff="out"`，CSS 换 `use href` |
| ② 走 | 200–900 | 信使沿走廊纵向从源行到目标行；横向两段各 160ms（出格 / 进格） | 位移 | 两层 wrapper，各一条 keyframe（见 4.3） |
| ③ 递交 | 900–1150 | 信使停在目标格出口；手里那张纸（`#state-handoff` 的 paper 道具）`translate` 到目标格桌面并淡出；目标行闪底（`animation-delay:1100ms`） | 道具 + 目标行 | 一条 `wt-give` keyframe；`in` 标记 |
| ④ 走回 | 1150–1600 | 信使反向走，1560ms 起淡出；源格吉祥物回到 `idle` 姿态 | 位移 + 淡出 | 同 ② 的 keyframe 反向，`animation-direction: reverse` |

**走回只有 410ms，而走去有 700ms** —— 同一段距离 1.7 倍速，观感是"快步回去"，可以接受。但如果 |Δ行| > 4，410ms 会快成闪现；那种情况下把 ④ 降级成**原地淡出**（不位移，`opacity 1→0` 用 240ms），省掉位移预算。

### 4.3 为什么这次可以做"走动"，而上一版否掉了"幽灵卡片飞行"

上一版（`docs/office-sidebar-ui.md` §3 候选 3）否掉飞行的理由是**要 `getBoundingClientRect` + portal + 处理滚动失效**。这次不需要，因为办公室本身就是一个**已知几何的场景**：

- 行高是常量 `--row-h`（B 是 64px），行号是 `--from` / `--to`（无单位整数，React 直接写进 style）。
- 信使是场景容器内的一个绝对定位元素，`top: calc(var(--from) * var(--row-h))`。
- 纵向位移 `translateY(calc((var(--to) - var(--from)) * var(--row-h)))` —— CSS `calc` 允许"无单位数 × 长度"。
- 横向只有两个固定值：左桌 `+78px`（工位中心 59 → 走廊中心 136）、右桌 `−79px`。

**零测量、零 portal、零滚动监听。** 这就是"把场景做成真几何"换来的东西 —— 也是我不建议在 A 的卡片网格上做同一件事的原因：卡片网格的行高随铭牌文案变，`--row-h` 就不是常量了。

### 4.4 降级与可达性

| 情况 | 处理 |
|---|---|
| `prefers-reduced-motion` | 不渲染信使；源行 `→ 小前` 文字保留 1600ms（信息不能丢）；目标行在 0ms 闪一次，不延迟 |
| 目标行不在视口 | 不做 `scrollIntoView`。滚动会把用户正在看的东西挪走；改为在走廊底部保留一个 4px 的"去向条"（warn 色，1600ms），指向目标行方向 |
| 信使 | `aria-hidden="true"`（纯装饰）。可达性由源行 `title` + `→ 小前` 文字 + 目标行 `title` 承担，现有 DOM 已够 |
| 交接发生在别的 tab | 现有 `handoffs` 是模块作用域 Map（`client.js:519`），标记会活到用户切回来；场景层只需在挂载时读一次 |

## 5. 七种状态在场景里长什么样

完整映射表在 `TOKENS.md`。这里只给一句话原则：

**身份色只上项圈，状态色只上「环 + 屏幕」。两个色系统永不共用同一个元素。**

原因是实测出来的：`state-warn-primary` = `#f59e0b`，而 pm 的 accent 也是 `#f59e0b`（`lib/roles.js:29`）—— 身份色和状态色在 pm 身上是同一个值。同理 frontend `#2d7ff9` vs business `#4176e6`、reviewer `#e04b4b` vs error `#ec1313`。所以两者一旦落到同一个像素上，用户就分不出"这是谁"和"他怎么了"。

七态各自的**至少两个通道**（全部静态可辨，动画只在进入状态时播一次）：

| 状态 | 通道 1 姿态 | 通道 2 屏幕字形 | 通道 3 环 | 通道 4 其他 |
|---|---|---|---|---|
| idle 待命 | 直立（基准） | 两条暗线 | 灰、静 | 项圈满色 |
| working 干活 | 前倾、肩抬 1.8、手在桌沿 | 4 行代码 + 光标 | business、pulse | 光晕亮 |
| waiting 等你回复 | 上身 −7°、头 −15°、**露一只眼** | 一个大光标 | warn、pulse | `?` 气泡 |
| done 有新结果 | **站起来**（整体 −3.5） | ✓ | success、实 | ✦ sparkle |
| error 异常结束 | 塌（头 +2、肩 +1.5、尾 −16°） | ✗ | error、shake | 光晕暗 |
| failed 入职失败 | 空心头（只有轮廓） | 空 + 红虚线框 | error、**虚线不转** | **无项圈** |
| provisioning 入职中 | 虚线轮廓 + 30% 填充 | 骨架条 + 虚线框 | business、**虚线转** | 项圈 55% |

`failed` 和 `provisioning` 是最容易糊的一对，所以它们刻意用了两套不同语法：**failed = 空心头 + 没有项圈**（"这个人从来没到"），**provisioning = 实心头 + 虚线描边 + 半亮项圈**（"正在画出来"）。灰度只用在这里 —— 项圈褪成灰 = 身份没建立起来。

## 7. 一句话交代设计意图

**办公室的价值不是"好看"，是让"谁在忙、谁在等我、东西在谁手上"这三件事在 300px 里不用读字就能看见。** 所以：身份放在不占宽度的项圈上，状态放在屏幕和环上，走动放在走廊里 —— 三件事各占一个通道，互不抢位。
